## P1: correctness and safety gaps the QA pass confirmed in code

4. **`next.config.ts` still ships debug settings:** `reactStrictMode: false` with a "temporarily disabled to debug multiple mounting" comment, and `largePageDataBytes: 300 MB`. Try `reactStrictMode: true` locally through the T7 checklist; if the double-mount problem is gone, keep it on and say so. Either way, lower `largePageDataBytes` or comment why 300 MB is needed. Flag both in the PR if unchanged.
5. **Approved-report audit trail is one snapshot deep.** Approving freezes the session and later messages start fresh (good), but there is no immutable record of who approved what, or the trace at approval time. Minimum for the demo: when a report is approved, the saved `data-analysis` part already carries status, facts and report; also keep the `data-trace` part of the submitting run in the same message (it is written today) and state in the submission that review is single-user. A real audit table with optimistic locking stays post-hackathon; do not build it now.
6. **Snapshot growth.** Every turn saves the full analysis snapshot, including full captured tool outputs, into `Message.parts`. Long chats with literature and variant lists grow fast and are re-sent to the client on load. Add a size guard: cap the stored snapshot (for example drop captured outputs for refs no fact cites, once a report is submitted) or document the limit. Measure one real dravet chat's saved message size before and after.
7. **No per-chat concurrency control.** Two tabs sending at once rebuild two sessions from the same history and race on save. Minimum: the route already loads the chat once; add an in-flight guard per chat id in the route (reject or queue a second concurrent run for the same chat) or document it as a known demo limitation. Do not build distributed locking.
8. **Rate limit fails open.** The per-user daily cap in `app/api/chat/route.ts` counts saved messages and returns `rate_limit:chat` over the cap, but a failed count query logs and lets the request through, and there is still no per-run token budget beyond `maxDuration = 300` and the 24-step cap. Keep fail-open (availability), but log the cap state and state the residual risk in the submission. Do not add Redis this week.
9. **Sandbox egress is open.** `lib/sandbox/python.ts` runs one networked microVM per chat and publishes `outputs/` to public Vercel Blob; the 20,000-char code cap landed, but a model-instructed script could still send uploaded data to an external URL. For the demo: state the risk in the submission, never run real patient data through it, and confirm no secret or `.env` value is reachable inside the sandbox. An egress allowlist stays post-hackathon.
